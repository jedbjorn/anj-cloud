# Device access protocol

## Enrollment

Use a trusted issuer and verify the TLS hostname. Bootstrap omits client certificates; protected DAV includes the device's certificate/private key. No bearer/password header substitutes for that key.

**Codes (decision #151, spec #35).** Every new invitation (Admin, `anj-cloud-admin invite`, the operator's `invite`, `anj-cloud-setup pair`) is a *pinned* code: the one-time secret followed by a prefix of the household CA certificate's SHA-256 (DER), in the same alphabet (`0-9A-Z` without `I L O U`, 5 bits per character), shown in groups of four. The two sizes are set in one place per side, `services/access/codes.py` (`PINNED_SECRET_BYTES`, `CA_PIN_BYTES`) and `apps/client/lib/core/gateway/dav_api.dart` (`pinnedSecretBytes`, `caPinBytes`); every length derives from them, `tests/pairing_code_vector.json` is the shared vector, and a pinned code may never have the legacy 32-character length (`codes.py` refuses to load). Today (operator 2026-11-05): a 7-byte secret (56 bits) and a 10-byte pin (80 bits), 17 bytes, **28 characters**, shown as 7 groups of four; 140 encoded bits carry 136, so the first character is always `0` or `1`. Separators and case do not matter. The server origin is not in the code. A pinned code is looked up only by the HMAC of all its characters, so a code whose CA part belongs to another server is simply unknown.

`GET /v1/ca` (no certificate, no query) answers the CA's public certificate as PEM (`application/x-pem-file`, `Cache-Control: no-store`) and nothing else. A device fetches it over TLS without trust, accepts it only if the first 10 bytes (80 bits) of its SHA-256 equal the code's, and then uses it as the profile's trust anchor for every later request; on a mismatch it stops ("This code is not for this server") and stores nothing.

Redeeming a valid, unexpired (10 minutes), unused pinned code approves the device in the same exchange: the gateway asks the console backend's `approve` (the issuer key never enters the gateway) with the fingerprint of the CSR it just reserved the code to. The exchange waits up to 20 s for it; if the approval takes longer, or the backend is unreachable, the answer is `pending` with `"approval": "automatic"` and the approval keeps running (one per pairing). The device repeats `POST /v1/enroll/status`, which waits for it again or starts it again after a failure. Each device paired this way gets exactly one audit entry (`device-paired`, actor `system`, written with its claim) and an ntfy alert through the backend's `admin-alert` ("anj-cloud: new device 'laptop' (fp 6150cf05) for sam": the computer name the device reported at enroll, never the admin's label for the code, and the first 8 hex of its key's SHA-256) that is **at least once**. The name is shown, stored and sent only as `naming.clean_device_name` makes it: printable ASCII (NFKD, combining marks dropped, any other character and `'` become `?`, whitespace collapsed, at most 40 characters ending in `...`, `unnamed` if empty), so the gateway's and the VM backend's different Unicode databases cannot disagree about it. The backend cleans a pairing alert's name and fingerprint (not 8 lowercase hex: `unknown`) instead of refusing it, and if an older backend still refuses the name the gateway sends the alert once more as `unnamed`. An alert counts as delivered only when the backend answers `sent` or `spooled`; the first failure of each alert episode is audited (`pairing-alert`, `alert-failed:<reason>`, actor `system`), and a gateway pass every 60 s re-sends any alert not yet confirmed, also after a restart, and audits and alerts a pinned invitation approved outside the gateway (setup's operator fallback). An admin approval by fingerprint of a pinned code (fallback) sends no alert of its own: the device gets the same one new-device alert whichever approval finished first. When a pinned code some device already holds is tried with another key, the requester gets the same 400 and the admin one alert (at least once) naming the first such device the same way: "anj-cloud: someone tried a used pairing code for alex: device 'kali' (fp 0badf00d)". Revoke stays one action (Admin, `anj-cloud-admin revoke`).

An unknown, expired, used (another key or CSR), denied or revoked pinned code, or anything that is not a code, is refused 400 `{"error": "Code not valid"}`, counting toward the source's block below; nothing says which part failed. Codes issued before this release (32 characters) keep the fingerprint approval below until they expire (rule 6).

`POST /v1/enroll` uses JSON `{ "code": "invitation", "csr": "PEM signed PKCS10 CSR", "label": "device label" }`. The key must be EC P-256. `label` is descriptive, at most 80 characters. Fingerprints are lowercase hex SHA256 of DER SubjectPublicKeyInfo. QR and manual forms normalize to the same characters; separators/case do not change the secret.

Pending response: `{ "state": "pending", "pairing_id": "uuid", "device_id": "uuid", "fingerprint": "64hex", "expires_at": 1793549400 }`. `POST /v1/enroll/status` takes the same code and exact signed CSR and returns the same pending identity or approved public certificate.

Approved response: `{ "state": "approved", "pairing_id": "uuid", "device_id": "uuid", "uid": "canonical-account-id", "rights": "write", "fingerprint": "64hex", "certificate": "PEM X509 certificate", "expires_at": 1794153600 }`. Rights are `read` or `write`. Verify the returned certificate's public key against the stored private key, and pin UID/origin to an existing client profile/root; a different UID must not silently take over a root.

Authorization binds both that public key and the exact issued certificate leaf. A new invitation may reuse a retained key/CSR after expiry or revocation, but its newly issued certificate never reactivates an older revoked leaf on the same key.

Enrollment is limited per source: at most 10 requests per minute across `/v1/enroll` and `/v1/enroll/status`, and 8 rejected attempts within a rolling 10 minutes block that source's enrollment for 15 minutes; both answer 429 with `Retry-After` (whole seconds until a request would be admitted: at most 60 for the rate limit, the time left of the 15 minutes for a block) and a JSON body `{"error": "Enrollment rate exceeded", "reason": "rate" | "blocked"}`; nothing states attempts or failures left. Paired devices on the same source keep syncing. `GET /health` answers `{"status":"ready"}` or 503 with `{"status":"unavailable"}`, without version details. Responses carry no `Server` header.

Other states are `denied`, `expired` and `revoked`. A competing key or different signed CSR returns400. Unfinished pairing expires at the original ten-minute deadline. Completed certificate retrieval may repeat after that deadline only while the same device remains active and its certificate unexpired; no new credential is created. Expired leaves require re-pairing; omit the expired certificate when accessing bootstrap.

## Certificate lifetime and pickup

Leaves are valid until the issuer's expiry (decision #44); ending access is explicit revocation, checked against the registry on every request. The operator may reissue an active device's leaf for its existing key and subject. Reissue never touches the device row's account binding or app token.

`GET /v1/device/certificate` requires the device's client certificate and takes no parameters. It returns `{ "device_id": "uuid", "certificate": "PEM X509 certificate", "expires_at": 1825158874 }` for the authenticated device's current leaf, with `Cache-Control: no-store`; missing certificate401, revoked/inactive403. Verify the returned leaf against the stored private key, the pinned issuer (client purpose) and the current leaf's subject before replacing it atomically; keep the working certificate on any failure.

After a reissue the previous leaf stays accepted, so a lost response or a crash before persisting never strands the device. Every earlier leaf is retired when the device first authenticates with the current one; it otherwise lapses at its own expiry. Revocation refuses all of them on the next request.

## Files

The canonical remote root is `/dav/`, bound server-side to `UID/anj-cloud/`. Requests use percent-encoded relative segments. Filename `#` and `?` are data encoded as `%23` and `%3F`; a literal percent is encoded as `%25`. Each URI path is decoded once and its filename segments encoded again for the backend. Raw query/fragment delimiters, encoded separators, dot segments, backslashes and malformed encodings return400. Only GET, HEAD, OPTIONS, PROPFIND, PUT, MKCOL, DELETE and MOVE are supported; COPY/LOCK/UNLOCK return405. PROPFIND requires Depth 0 or 1. Tagged DAV `If` forms are unsupported. Missing certificates return401, inactive devices/read-only write attempts403.

Literal escape-looking filename data is supported: `a%20.txt` uses `a%2520.txt` on the wire, and a literal `%2e%2e` directory uses `%252e%252e`. These remain ordinary names after one decode; raw `%2e%2e` still means a forbidden traversal segment. The bounded filename fixture directly qualifies distinct names, bytes, listing, MOVE and sharing against pinned Nextcloud 33.0.10; no filename mapping or further decoding is applied.

New PUT/MKCOL require `If-None-Match: *`. Existing PUT, DELETE and MOVE require one quoted concrete `If-Match` ETag; missing baseline428, wildcard/ambiguous baseline400, stale baseline412. MOVE additionally requires `Overwrite: F` and an absolute same-origin `/dav/` Destination. Root replacement/deletion is forbidden. Authoritative checks and backend mutations share one process-wide lock across accounts/share aliases.

Nextcloud keeps a file's ETag when it is overwritten within the whole second of its previous write (its cache scanner reuses the stored ETag while the one-second storage mtime is unchanged), so readers of the first version would never see the second and its stale `If-Match` would still pass. An overwriting PUT whose target was last modified in the backend's current second (`getlastmodified` against the backend's `Date`, both read under the lock) therefore waits, holding the lock, until that second has passed: about one second, only for such back-to-back overwrites. An unreadable time waits the same. An overwrite that still returns its previous ETag is logged as a warning. Writes made to Nextcloud without the gateway are not covered.

ETags and ranges retain Nextcloud semantics. Successful PROPFIND returns207 with hrefs rewritten to absolute gateway URLs. GET ranges return206 where supported; Content-Length refers to unchanged wire bytes. Cookies, supplied identity/Authorization headers and arbitrary redirects are never forwarded. Backend error bodies are withheld to avoid internal-path disclosure; status codes remain observable.

Dev PUT requires Content-Length and a maximum 64 MiB request; uploads are privately staged under a bounded budget. A disconnected/revoked caller receives no commit response. Bytes already accepted and dispatched to Nextcloud may commit after client cutoff, while the server retains mutation ordering. Reconcile versions after reconnect instead of assuming rollback.

Oversized PUT returns413 with JSON `{ "error": "transfer_limit", "actual_bytes": 67108865, "max_bytes": 67108864 }`. Retain the local source and pending upload intent. Chunked uploads are deferred; the configured request limit is explicit rather than a universal file-size promise.

## Portable names

Decision #120: a name that cannot exist on Windows or macOS is refused for every writer. A new PUT (`If-None-Match: *`), MKCOL and a MOVE destination are refused when the final name is a Windows reserved device name (CON, PRN, AUX, NUL, COM1-9, LPT1-9, any ASCII case, with or without an extension), ends in a dot or space, contains `< > : " / \ | ? *` or a C0 control character, or differs from a name already in the target folder only by case or Unicode normalization (canonical caseless matching, `NFD(casefold(NFD(name)))`; a case-only rename in place is allowed). The answer is `422` with `{"error": "name-not-portable", "reason": "reserved" | "trailingDotOrSpace" | "invalidCharacter" | "clash", "message": "..."}`, never a path. The name rules are refused before the body is read (the connection then closes); the sibling check runs under the single mutation lock against a Depth 1 listing of the target folder (resource types only, at most 8 MiB, else 503), so no other create through the gateway can slip in between. Existing items are never renamed or touched: reads, overwrites (`If-Match`) and deletes of a blocked name work as before. `POST /v1/shares` refuses a folder whose own name is blocked (422, `code` and `reason` beside `error`); Nextcloud picks the recipient's mount name on an exact collision, and a case-only collision in the recipient's `Shared/` is outside the owner's request. The rule lives in `portable_names.py`; the clients' `NamePolicy` is the same rule, and both run `tests/name_policy_vectors.json` over the Unicode tables generated by `tests/name_policy_gen.py`.

## Added times

Nextcloud has no cross-device "added" date (`nc:upload_time` resets on every content update; `nc:creation_time` is client-supplied). The gateway therefore records one (decision #56): when a `PUT` through it returns `201 Created`, it stores `(account UID, file ID, its own UTC clock)`, taking the file ID from Nextcloud's `OC-FileId` response header (zero-padded `oc:fileid` plus the instance ID). The first record for a file wins. A `204` overwrite, `MOVE`, `MKCOL` or failed upload records nothing. Recording never changes the upload response: a missing header or a failed write leaves the file undated. A successful `DELETE` through the gateway removes that file ID's row (descendants of a deleted folder keep theirs; clients only look up IDs they list).

`GET /v1/files/added[?after=CURSOR][&limit=N]` requires the device's client certificate and returns only the device's own account's rows, oldest first: `{ "added": { "646": 1793639049.0 }, "cursor": 12, "more": false, "reset": false }`. Keys are `oc:fileid` values, times are Unix seconds. Pass the returned `cursor` as `after` for the next call; a steady-state call returns an empty map. A page holds at most 1000 rows (`limit` 1-1000); `more` means another page is ready. `reset` means the cursor is beyond every issued sequence (a replaced registry): start again from 0. It is a read and is served while writes are fenced. Unknown or repeated parameters return400, missing certificate401, revoked/inactive403. A gateway without this route answers404; clients treat that as "no dates".

## Media fetch

Spec #42 (decisions #179, #180). A gateway started with `ANJ_FETCH_SPOOL` (the spool volume it shares with the fetch worker, `services/fetch/`) serves four routes; without it they answer 404 and clients show no Downloader tab. Each requires the device's client certificate, acts only as that device's account, takes no query string (400), answers JSON with `Cache-Control: no-store`, and is logged with route class `fetch`: never a link, a title or a path.

| Route | Answer |
|---|---|
| `POST /v1/fetch/jobs` `{"urls": [...], "kind": "audio"\|"video", "height": 1080\|720}` | 202 `{"jobs": [rows]}`, the new rows newest first. `height` is required for video only. 400 malformed, a non-http(s) link or more than 50 links; 403 a read-grant device; 429 over 500 unfinished rows for the account; 507 under 10% free on the data disk; 503 worker not running or writes fenced for maintenance (an import in progress does not refuse) |
| `GET /v1/fetch/jobs` | `{"jobs": [rows]}`, the account's rows newest first |
| `DELETE /v1/fetch/jobs/{id}` | 204: cancels a waiting or running job (it becomes `cancelled`), or removes a finished row. 404 for an unknown or another account's id; 409 while the file is being saved (`placing`); 403 a read-grant device |
| `POST /v1/fetch/jobs/clear` | 204: removes the account's finished rows. 403 a read-grant device |

A row: `id`, `state` (`waiting`, `checking`, `downloading`, `placing`, `done`, `rejected`, `failed`, `cancelled`), `kind`, `url` (the submitted link, returned only to its own account), `title` (null until known), `percent` (an integer, present only while downloading), `path` (account-relative, such as `Music/Title.m4a`, once placed; for a playlist link the folder its items go to), `message` (one plain sentence on a terminal row that is not a plain success, else null: a `done` row carries one only when it adds information, a lower height than asked or a playlist's "Added N items…"), `height` (video: the height obtained once known, else the one asked for; the short side, so a 1080x1920 portrait video is 1080; audio: null), `submitted` and `finished` (Unix seconds; `finished` null until terminal). Errors are `{"error": "sentence"}`.

**Queue.** One job runs at a time for the whole server. The next is taken from the account whose oldest waiting job has waited longest, counting from when that account's previous job left the running slot, so accounts alternate between a long playlist's items. A waiting job that reaches the head while the data disk has under 10% free fails ("Server storage is almost full."), and so does a running one when free space falls under that floor. A job with no progress for 5 minutes, or checking and downloading for more than 3 hours, fails. Finished rows are removed after 7 days. Rows survive restarts: a job checking or downloading when the gateway or the worker stopped returns to `waiting` once, then fails ("The download was interrupted twice."); a job being saved resumes its import from the staged file.

**Playlists.** A submitted link that is a playlist becomes one row per item (at most 200, and within the account's 500), placed in `Music/<playlist title>/` or `Videos/<playlist title>/` (an existing folder of that name, also apart from case and accents, is reused); the link's own row turns `done` and says how many were added. A link to a video that also carries a list parameter is one item.

**Import.** The gateway imports the worker's checked file with the submitting device's own credential in two phases. It first uploads the staged file, without the household's write lock, to a temporary name outside the synced root (`files/<uid>/.anj-fetch-<run>.tmp`; the gateway serves only `files/<uid>/anj-cloud/`, so no client lists it), while every other device's writes go on. Then, under the single mutation lock and write fence, it chooses the final name and moves the file there with `MOVE` and `Overwrite: F` (a rename), records the added time, and releases the lock. The name rule is the upload's: the title made portable (blocked characters become `_`, control characters and bidirectional controls and the BOM are removed while other format characters such as ZWJ and ZWNJ are kept, leading and trailing dots and spaces go, at most 150 characters and 200 bytes, a Windows device name gets `_`, empty becomes the site's media id) plus ` (2)`, ` (3)`… when a name is taken exactly or apart from case and accents. Nothing is overwritten. The 64 MiB client limit does not apply, the 8 GiB item limit does (Nextcloud's internal `APACHE_BODY_LIMIT` is 8 GiB + 1 MiB for this; clients never reach Nextcloud). The top folder is created when missing. A revoked device or disabled account fails the job ("This device no longer has access."). While writes are fenced the import waits in `placing`; while Nextcloud answers 503 (maintenance, such as the nightly backup) it waits with a backoff from 15 s to 5 minutes and fails after 2 hours ("The file could not be saved to the cloud."). Any completed answer to the `MOVE` clears the fence; with no answer the target is read back, and the fence stays closed for operator recovery only when that is inconclusive. A gateway restart during the upload phase leaves no fence and resumes from the staged file. Temporary files are removed on every failure and swept when the gateway starts. The spool keeps no file for a terminal job.

**Spool.** Everything the worker writes is untrusted: the gateway reads only names it chose (`status.json`, `media.m4a`/`media.mp4` in the run's own directory, the worker's `heartbeat.json`), never follows a link, bounds sizes, validates every field, checks that the staged file is an MP4, and maps the worker's outcome codes to its own sentences. The protocol is documented in `fetch.py`.

## Trash

Spec #44. Four routes over the calling device's own Nextcloud trash (`/remote.php/dav/trashbin/<uid>/`, with the device's own credential), authenticated by the device certificate exactly like `/dav/`. Only items whose original location is under `anj-cloud/` exist for them: anything else in the account's trash is never listed, restored or deleted. They take no query string (400), answer JSON with `Cache-Control: no-store` and are logged with route class `trash`, never a name or path. Errors are `{"error": "sentence"}`.

| Route | Grant | Answer |
|---|---|---|
| `GET /trash/` | read | `{"trash_days": 7, "items": [{"id": "174", "path": "Documents/a.txt", "kind": "file"\|"folder", "size": 12, "deleted": 1794522933, "expires": 1795127733}]}`, newest first. `id` is the trash item's Nextcloud file ID; `deleted` and `expires` (`deleted` + `trash_days` days) are Unix seconds |
| `POST /trash/{id}/restore` | write | `{"path": "Documents/a (restored).txt", "renamed": true}`: the item's final path. 404 `Not in Trash` |
| `POST /trash/restore` `{"ids": ["174", ...]}` | write | `{"results": [{"id", "path", "renamed"} or {"id", "error", "status"}, ...]}` in request order: up to 500 items restored with one listing and one hold of the lock, each by the single restore's rules (Undo of a bulk delete). After an unknown outcome the rest answer 503 |
| `DELETE /trash/{id}` | write | 204: deleted permanently. 404 `Not in Trash` |
| `DELETE /trash/` | write | `{"deleted": 3}`: every `anj-cloud/` item deleted permanently; other items stay |

Restore runs under the single mutation lock and write fence with a recorded intent, as its own task behind a shield like `/dav/` mutations, so a client that disconnects never leaves it half done. Missing parent folders are created first: Nextcloud would otherwise restore the item at the account's top level, outside `anj-cloud/`. A missing folder is not recreated when a folder with the same name apart from case or accents is there (409), nor anywhere under `Shared/` (409 "The share this came from is no longer here": the share is gone or was renamed). Nextcloud also restores to the top level when the caller may not create in the folder (a share turned View only), so the folder's `oc:permissions` must allow creating a file (`C`) or folder (`K`) there, else 403 "You can't add to the folder this came from". Success is reported only when the item is read back in its folder; otherwise the outcome counts as unknown. When the original name is taken, exactly or apart from case and accents, the item is restored as `name (restored).ext`, then `name (restored 2).ext` and so on; nothing is overwritten. Nextcloud restores to the original location whatever name is asked for and renames only exact collisions itself, so the gateway renames what it restored to its own free name when the two differ. A lost answer is read back: gone from the trash with a new name in the folder means restored, still in the trash means not (502); only an inconclusive read-back leaves writes fenced (503) for operator recovery. Delete and Empty read a lost answer back the same way. While writes are fenced every write answers 503; the list is a read and is served. A read-grant device lists, and gets 403 for the three writes.

`trash_days` is the deployment's retention, set in Nextcloud as `trashbin_retention_obligation` = `D, D` (deleted after exactly D days; Nextcloud's expiry job in the cron container removes an item between D days and D days plus one cron cycle after its deletion). Setup and every upgrade read the setting back and store it in the gateway (operator action `{"action": "trash-days", "days": D}`, best effort: a gateway from before Trash, after a rollback, refuses it and the deployment continues); until then the gateway advertises 7. Dev and review stacks take `ANJ_TRASH_DAYS`, production `trash_days` in `state/stack.json`, default 7.

Shares (Nextcloud 33.0.10, `deploy/trash_fixture.py --case share`): a recipient's delete inside someone else's share lands in both trashes, the owner's (original location under the owner's folder, deleted by the recipient) and the recipient's own (under its mount). Each side's Trash lists only its own item. Either side's restore puts the file back in the share for both; the other side's item stays in its trash until it expires.

## Operator boundary

The operator API exists only on a private Unix socket. The local CLI creates invites, compares fingerprints, issues certificates/Nextcloud credentials, registers household accounts, grants/changes/removes directory shares, revokes devices and reconciles uncertain provisioning. It is not a public client API. See the [development guide](../../deploy/README.md) for commands, trust distribution and scoped write-fence recovery.

## Directory sharing

Spec #26. Eight routes, each authenticated by the device certificate exactly like `/dav/` (401 without one, 403 for a revoked device or a disabled account), acting only as that device's account. No query strings; JSON bodies within the 16 KiB cap; `Cache-Control: no-store`; error bodies `{"error": "..."}` never carry a path. Logged with route class `share` (method, status, bytes, duration; never a path, folder or display name).

| Route | Answer |
|---|---|
| `GET /v1/household/users` | Enabled household accounts other than the caller: `[{id, display_name}]` |
| `GET /v1/shares/outgoing` | Shares of the caller's folders: `[{share_id, path, recipient_id, recipient_display_name, permission}]` |
| `GET /v1/shares/incoming` | Shares made to the caller: `[{share_id, path, owner_display_name, permission, owner_unavailable}]`; `path` is the mount, `Shared/<folder>` or, for a placed share, `Documents/<folder>`, `Music/<folder>` or `Videos/<folder>` |
| `POST /v1/shares` | `{path, recipient_id, permission}` → 201 with the new row |
| `PATCH /v1/shares/{share_id}` | `{permission}` → 200 with the row |
| `DELETE /v1/shares/{share_id}` | → 200 `{"state": "removed"}` |
| `DELETE /v1/shares/incoming/{share_id}` | The recipient leaves a share made to it (decision #157) → 200 `{"state": "left"}`; the owner's folder is untouched |
| `POST /v1/shares/incoming/{share_id}/rename` | `{name}` (at most 250 bytes of UTF-8, a portable name) → 200 `{"state": "renamed", "path"}`: the recipient renames the shared folder for everyone (decision #155); `path` is the caller's mount afterwards |

Sharing has one level, full access (decision #155): a share is created or changed only with `permission` `edit` (Nextcloud 15); `view` (1) is refused with 422 "Sharing has one level: full access" and is only read, from a share made earlier, which an owner can raise to `edit`. The share bit is never set. A read-grant device may list but gets 403 on POST/PATCH/DELETE. Errors: 400 malformed body or unexpected field (an owner is never named), 404 unknown or foreign share or missing folder, 409 recipient already has access, 422 not a folder, the root, `Shared` or beneath it, the top-level `Documents`, `Music` or `Videos` themselves ("Documents, Music and Videos are private"; folders inside them can be shared; new shares only, spec #34 P4, decision #148), or a recipient not on the household list, 502 a known backend refusal (that share's scope is fenced), 503 while writes are fenced, in maintenance, or after an unknown outcome (household-wide fence).

**Delete, leave and rename (decisions #150, #155, #157).** The owner deleting the shared folder is an ordinary delete: it is gone for everyone, into the owner's trash (an operator restore from there brings back the files and the share at each recipient's placed name; checked on Nextcloud 33). A recipient deleting the shared folder on a device (in `Shared/` or placed) leaves the share once the removal has settled: the folder gone for the watcher's longest delay plus its quiet period (about 12 s), with nothing else going missing under it, its top folder or `Shared`, a fresh check that it is still gone and its top folder or `Shared` is still the same folder, and its identity on record (without one it is restored). Deleting a whole `Documents`, `Music` or `Videos`, or `Shared` (also when it is created again empty), restores everything in it, shares included. Files inside a shared folder stay truly shared: anyone adds, edits, renames or deletes them for everyone (deletions inside wait for the same settle and are never sent while the shared folder itself is gone; a recursive delete of the shared folder that stalls longer than the settle sends the files it already removed as ordinary deletes, accepted by decision #158). Renaming the shared folder in place (case-only included), by anyone, renames it for everyone (a folder counts as the renamed share only when it has the share folder's file number and holds one of its known files under the same name and number; otherwise the removal is a leave); moving it into another folder keeps the share where it is and the moved copy becomes the recipient's own. Rename for everyone: a recipient's write-grant device, a share in its own incoming list with full access (View only: 403). The gateway acts on the owner's side with the owner's own write-grant device credential, never a minted token; without one it answers 409 "The owner's device is needed" and the client retries later. It is an owner-side `MOVE` in the same folder (`Overwrite: F`); a name the owner already has there, exactly or apart from case and accents, or a top folder's name at the root, is refused with 409 "The owner already has a folder with this name", never suffixed; names are at most 250 bytes of UTF-8 and portable. The caller's mount then takes the name (kept when that name is taken in its place); every other recipient's mount follows at that recipient's next incoming read. It runs under the single lock with intent `share-rename`, every path built before the intent is recorded; the intent is always finished: a known refusal fences that share (502), an unknown outcome is read back on the owner's side, and when that answer is unreadable too the share is fenced (503), never the household's writes. A rename whose follow-up read of the other recipients fails answers 502 after the owner's folder was renamed; the client's retry finds it renamed and finishes the other recipients.

`owner_unavailable` marks a share whose owner's account is disabled: Nextcloud hides it, the gateway reports it from the recipient's last seen mount, and clients pause that folder instead of inferring deletions.

**Placement (spec #34 P6, decision #149).** A new share of a folder inside the owner's top-level `Documents`, `Music` or `Videos` is mounted in the recipient's same folder instead of `Shared/`. Nextcloud mounts it in `Shared/` first; the gateway then moves the mount as the recipient (WebDAV `MOVE`, `Overwrite: F`; the move and its check under the single-writer lock, the reads before it outside): at once when the recipient has an active write-grant device, else at a write-grant device's next `GET /v1/shares/incoming`, before the list is read. A read-grant device never moves anything, so its list names the share in `Shared/` until a write-grant device of the account reads. Before moving, the gateway checks that the folder at the share's target is this share's mount (its `oc:fileid` and owner are the shared folder's). An attempt that cannot be decided (a 5xx, a lost answer, an unreadable folder) is retried after 30 s, doubling to at most an hour, six times; then the share stays in `Shared/`. The name is the folder's own; if the recipient already has that name in the folder, exactly or apart from case and accents, it is `<name> (<owner display name>)` (the owner's account ID when the display name is not portable); if that is taken too, or Nextcloud refuses the move, the share stays in `Shared/`. The registry's `share_placement` table records each such share (`pending`, `placed`, `kept`). Shares from anywhere else, and shares created before this, stay in `Shared/`. Confinement: a recipient mount is allowed only as a direct child of `Shared/` or, for a share recorded for placement, of that one folder; a new share that lands anywhere else is removed at once (502, or the cleanup fence when the removal fails), and such a mount is never listed as incoming. A folder that is, or is inside, a share made to the caller cannot be shared (422 "Folders shared with you cannot be shared"). Leaving runs under the same lock and fences as the owner's routes (intent kind `leave`); an unknown outcome is read back at once as the recipient, and any failure fences only that share. A recipient-side cleanup (a placement that escaped) is recorded under the share's owner.

## Client releases

Spec #28 G1, spec #37 U-core, decisions #108 Q6 and #159. The household server is the clients' update source: the operator publishes a signed client package with its manifest, and every paired device fetches both over its own mTLS connection. The gateway never signs and never verifies a signature; it stores what the operator published and the client verifies it before it offers to install. Android (`android-arm64`): SHA-256 and size, the APK signing certificate against `signer_sha256` and the installed app, `version_code` greater than the installed one. Desktop (`linux-x86_64`, `macos-arm64`, `windows-x64`): the manifest's Ed25519 `signature` by the household release key, whose public half is built into the app, then SHA-256, size, target and a greater `version_code`; a compromised gateway can therefore not make a desktop client install anything.

| Route | Answer |
|---|---|
| `GET /v1/client/releases/{target}` | The current manifest with `Cache-Control: no-store`: Android `{target, version, version_code, size, sha256, signer_sha256}`; desktop `{target, version, version_code, size, sha256, key_id, signature}` plus an optional `min_client_version_code`; 404 `{"error": "no_release"}` when nothing is published |
| `GET /v1/client/releases/{target}/package` | The current release's bytes: `Content-Length`, `Accept-Ranges: bytes`, `ETag: "<sha256>"`, `Cache-Control: no-store` |

`{target}` is `<os>-<arch>` from a fixed allowlist (`services/access/release_manifest.py`): `android-arm64`, `linux-x86_64` (served as `application/gzip`), `macos-arm64` and `windows-x64`; an unknown target answers 404 `{"error": "unknown_target"}`. Desktop manifests: `key_id` is the first 16 hex characters of the release key's SHA-256; `signature` is the base64 of the 64-byte Ed25519 signature over `signed_message` in the same file: the UTF-8 lines `anj-cloud release v1`, then `target …`, `version …`, `version_code …`, `size …`, `sha256 …`, `key_id …` (name, one space, value), each ending in a newline. The Linux manager (`apps/client/tool/linux_install.py`) and the Dart client build the same bytes; `apps/client/tool/testdata/release_signature_vector.json` is the shared vector. The optional `min_client_version_code` (1 to `version_code`) is not signed: a client below it only shows "Update required". The gateway checks the shape of every field and nothing more. Both routes authenticate exactly like `/dav/` (401 without a certificate, 403 for a revoked device or a disabled account, both before any target is looked at), any active device of any account may use them, read-grant devices included, and they are served while writes are fenced. No query strings (400). One byte range per request: `bytes=a-b`, `bytes=a-` or `bytes=-n` answer 206 with `Content-Range`; a range past the end is 416 `Content-Range: bytes */<size>`; several ranges or a malformed header send the whole package. Resume with `If-Range: "<sha256>"`: if the release changed meanwhile the whole new package comes back (200). The package is streamed a 256 KiB chunk at a time, each write waiting for the connection to drain, so the gateway never holds the file in memory and a link that is moving data never reaches the production ingress's 120 s idle limit. 30 requests per device per minute across both routes and two downloads at once per device (429). A chunk that does not drain within 120 s, or a download still running after 2 hours, ends the connection, so a reader that stalls or drips cannot hold a slot; so does a read failure after the headers are sent. The gateway never writes a second response into a started body: the client sees a short body and resumes with `Range` or retries (logged `stream-timeout` or `stream-failed`). Revoking a device or disabling its account aborts its download in flight. Logged with route class `release` (method, status, bytes, duration, device); never a package name or a path, and no answer or header names a file.

Publishing is the operator's `release-publish` (deploy guide): the package is streamed over the private socket (`PUT /operator/release/{target}`, manifest in `X-Anj-Release-Manifest`), written to a temporary file on the state volume while it is hashed, refused if its size or SHA-256 differs from the manifest or its `version_code` is not greater than the current one, then fsynced and renamed into place; the manifest is swapped in last, by an fsynced rename. One publish runs at a time. The current release and the one it replaced are kept per target; older ones are removed after the swap, and a download that had already opened one finishes. The publish succeeds once the manifest is swapped: if removing older releases fails, the answer says `"prune": "failed"`, a `release-prune-failed` event line is written and the next publish removes them. A symlink or a file in place of `releases/`, `releases/<target>/` or `releases/.incoming/` refuses every publish (400) and download (503). Uploads cut off by a crash or restart are removed when the gateway starts. The socket's `releases` action lists the served manifest and the version codes kept per target. Each publish writes one `release-publish` event line (target, version code, size, SHA-256).

Publishing from the VM host is `deploy/release.py publish` (signs desktop manifests; checks commit, `version_code` and signer) over this `release-publish`. Android release APKs are built with `apps/client/tool/android/release_android.py build`, published with `release.py publish --target android-arm64`, and offered for first installs (decision #131) with `release_android.py github-release` (a dry run unless `--create`, which needs the operator's go-ahead).

### Rotating a release key

No command rotates a key and there is no remote revocation: every installed app keeps trusting the key it was built with (desktop) or the certificate it was installed with (Android) until it is replaced by hand. Rotate only when a key is lost or may be known to someone else; until the steps below are done, publish nothing.

**Household release key (desktop, decision #161).** `release.py keygen` refuses while either half of the old key exists, so:

1. Move the old private key out of the key directory, without deleting it until the new key works: `mv ~/.local/share/anj-cloud/release-key/release-key.pem ~/.local/share/anj-cloud/release-key-retired-$(date +%F).pem` (keep it 0600, outside every worktree).
2. Remove the old key line from the generated public key file and the old `[release] public_key` and `key_id` from your deployment profile (`apps/client/assets/release/household-release-key.pub` is untracked and rebuilt from the profile by `apps/client/tool/apply_profile.py`).
3. Run `python3 deploy/release.py keygen`. It writes the new private key (0600, directory 0700) and the new public line, and prints only the new key_id and public key SHA-256.
4. Put the new public key line and key_id in your deployment profile (`[release]`), then record the new key_id and fingerprint as a decision that supersedes #161.
5. Package a release from a commit that carries the new key and publish it with `release.py publish`. Apps that still carry the old key refuse it ("signed by another key"), so on every desktop install that release once by hand: Linux `anj-cloud update <archive> --sha256 <hex>`; macOS and Windows through their installer. From then on that device updates itself again.
6. When every device runs a release with the new key, destroy the retired private key and its offline copy, and give the operator the new key for the offline copy.

**Android signing key (decision #108 Q6).** Android installs an update only when it is signed with the installed app's certificate, so a new key means one uninstall and a new pairing per phone; the files under the app's storage are lost with the uninstall (the server keeps everything that was synced). Move `~/.local/share/anj-cloud/signing/android/` aside, run `release_android.py keygen`, put its certificate SHA-256 in your deployment profile (`[release] android_signer_sha256`) and record a decision, build and publish a release (and a GitHub release for the reinstall), then on each phone: uninstall AnJ Cloud, install the new APK, pair again. Phones that still run the old app refuse the new release in the app ("different key"), which is expected: the reinstall is how they move to it.

## Owner console

For the owner console (spec #27) the socket also answers `settings-get`, `settings-set` and `status`. `settings-set` takes `upload_limit_bytes`, a whole number from 1 MiB to 64 MiB (larger values need Feature #6), applies it under the single-writer lock, persists it in the registry (it then wins over `ANJ_MAX_TRANSFER_BYTES` across restarts) and advertises it in `X-Anj-Upload-Limit` on the next DAV response. An upload that already started keeps the limit it was admitted under. `status` reports backend readiness, the write fence's state and operation kind (never its path), the number of transition leaves and the limit in force. The registry keeps each device's own enrollment label from its first reservation.

## Household administration

Spec #27, decision #87. The Admin section of the client calls these routes on the same mTLS listener as DAV; there is no other door. The admin role is on the account (`accounts.admin`), never on a device. Every `/v1/admin/` request is authorized afresh: an active device whose account exists, is enabled and holds the role (403 `not-admin` or `account-disabled`); mutations also need a write-grant device (403 `read-grant`). 60 admin requests per device per minute (429). Logged with route class `admin`; no codes, fingerprints or bodies.

| Route | Effect |
|---|---|
| `GET /v1/account` | Any active device: `{uid, display_name, admin}` of its own account |
| `GET /v1/admin/users` · `POST /v1/admin/users` | List; add `{uid, display_name}`: a NEW account only (console backend `user-add`, then the account row). The id rule (`services/access/naming.py`: the registry's 1-32 of `[a-z0-9-]`, and for a new account also a leading letter; existing accounts such as `1amy` stay manageable) and printable display names are checked before anything is created; reserved ids (`anj-admin`, `admin`, `recovery-cli`, `system`, `bootstrap`) and existing non-household server accounts are refused (409). Before the backend is called the account is recorded as setup incomplete (SC-041), so a call that is cut, times out or never answers, or a created account whose household row did not follow, is listed in `users` with `setup_incomplete` ("Setup incomplete — add again to finish" in Admin) and finished by adding it again (`resume`; the backend still refuses a server account it did not create, and the record is then dropped). The record is dropped at once when the backend certainly created nothing (unreachable socket, or a refusal) |
| `POST /v1/admin/users/{uid}/enabled` · `/admin` | `{enabled}` / `{admin}`; last-admin rule |
| `GET /v1/admin/devices` · `POST …/{id}/revoke` · `…/reissue` | Devices with label, grant, last seen, expiry, `this_device`, and for a device paired by a pinned code its `computer_name` and `fingerprint_short` as its alert names them (spec #35); revoke refuses at once, then the backend removes the app token (retried until confirmed) |
| `GET /v1/admin/invitations` · `POST /v1/admin/invitations` | Pending enrollments and open codes (never a code or fingerprint); create `{uid, grant, label}` returns the code once |
| `POST /v1/admin/invitations/{id}/approve` · `…/deny` | Approve `{fingerprint}` typed from the new device (compared here before the backend signs); deny or cancel |
| `GET`/`PUT /v1/admin/settings` | Upload limit `{upload_limit_mib}`, 1-64 |
| `GET /v1/admin/health` · `POST /v1/admin/test-alert` · `GET /v1/admin/audit?after=&limit=` | Gateway and backend facts; one ntfy test; audit newest first |
| `GET /v1/admin/operations/{id}` | The result of this device's own long action (below); 404 `operation-unknown` for any other id or device |

**Long actions (SC-041).** Production HAProxy passes TLS through untouched and closes a connection idle for 120 s; it cannot see the path, so admin routes keep the same limit as DAV. Every admin request is therefore answered within 25 s (`OPERATION_HOLD`): an action still running then (an approve or user add waiting on a busy console backend, up to its 300 s limit) keeps running in the gateway, whatever happens to the connection, and the request answers 202 `{operation, state: "running", message}`. The same device then calls `GET /v1/admin/operations/{operation}`, which waits up to 25 s again and returns 202 while it runs, then the action's own status and body. A finished result can be collected again for 10 minutes, then it is forgotten (the action was audited when it finished). The client polls this way for up to 345 s per action; one request never waits more than 60 s (`tests/test_admin_timeouts.py` ties these to HAProxy and `BACKEND_TIMEOUT`).

Every mutating request carries `expect`, the target's `revision` from its listing; a changed target is 409 `stale` with the current revision. Destructive actions (disable, role change, revoke, reissue, upload limit, deny or cancel) first answer 428 with `{title, effect, confirm_token, second_factor_typed}`; the client shows that text and resends with `confirm` (single use, bound to the device, action, target and revision, 2 minutes). Revoking the last admin's only device, or one's own device, also needs `typed` equal to the account id. The last enabled admin cannot lose the role or be disabled (409 `last-admin`, checked in the same transaction as the change). Every admin request's failure is curated (unexpected errors: 500 `error`, plain text). Every mutating attempt, including refusals and unexpected errors, is recorded in the registry's `admin_audit` (newest 10,000): time, actor uid and device (or `recovery-cli`), action, target ids, result class.

Work needing the issuer key, `occ` or PM2 goes to the console backend over `ANJ_CONSOLE_SOCKET` (default `/run/anj-console/backend.sock`); when it is unreachable those routes answer 503 `console-backend-unavailable` and the views keep working. The operator socket's `admin` action runs the same operations for the recovery CLI (actor `recovery-cli`, no confirmation tokens), plus `accounts-import` (first-admin import) and `audit-import` (entries the CLI wrote while the gateway was down). After a successful role change, disable, revoke, or an invitation or approval for another account (decision #103), the gateway asks the backend's `admin-alert` for one ntfy message (fixed template, ids only); a failed alert never fails the action and is audited as `alert-failed`. Disabling an account with no active device goes to the backend's `account-disable`, the operator CLI's path with a temporary owner token (decision #101).
